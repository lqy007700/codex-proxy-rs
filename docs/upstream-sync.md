| 范围 | 当前约束与操作 |
| --- | --- |

| 插件 | RPC `v4`、`scheduler v3`；旧插件使用匹配 SDK 与 CLI 重建，完整合同以 [宿主兼容清单](../backend/crates/gateway-plugin/runtime/plugin-host-compatibility.json) 为准 |
| 代理 API | 创建与测试接收 1–100 项数组，单项也使用数组；检查逐项结果，不根据批次 HTTP 200 推断全部成功或自动重试整个批次 |
| 请求查询与导出 | 管理端保留 `scope` 参数与诊断包 `schemaVersion: 6`，不直接切换为上游的 `status` 参数或 `schemaVersion: 5` |
| 耗时字段 | 调用方不再依赖四个细分引擎 TTFT/TBT 字段，保留请求级首字、API 开销和引擎耗时 |
| 工具链与子模块 | Node.js `26.12.0`、Rust `1.99.1`；UI 和插件按宿主锁定提交同步，不自行追踪各子仓库最新分支 |

## 每次同步时维护

1. 核对工作区与远端，记录当前发行 tag、提交和目标上游稳定 tag；只读分析冲突和完整差异，分别列出采用、保留和待选项
2. 对照[二开行为与维护索引](fork-behavior.md)逐项追踪调用链，核对自动合并的代码，不能只检查冲突文件；需要改变保留项时先取得用户选择
3. 检查当前已部署迁移的编号与 checksum，新增迁移只追加；同时核对 API、插件合同、子模块和构建工具链
4. 按影响验证请求恢复、页面交互、数据库升级和发布流程；通过、失败、跳过和未执行分别报告，不把旧版也存在的失败计为通过
5. 就地更新本文的基线、能力表和待选提交，并同步二开维护索引，移除已失效项；逐版本的发行变化留在对应 tag 的 `release/notes.md` 与 Release，不在本文追加历史章节
6. 按本轮授权分别完成本地修改、提交推送、发布或部署；用户要求停止跟踪发布时，交付任务链接，不把成功触发当作产物发布成功
